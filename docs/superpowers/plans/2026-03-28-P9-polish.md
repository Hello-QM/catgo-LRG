### 1A: Provenance Tests (3 failing)

**Root cause:** `find_duplicate()` in `server/catgo/workflow/provenance.py` searches for candidates by iterating `input_hashes.values()`, but the test at line 160 calls `find_duplicate(db, "geo_opt", {}, params_hash)` with an **empty** `input_hashes` dict. The `for h in input_hashes.values()` loop never executes, so `candidate_tasks` stays empty and the function always returns `None`.

The `find_duplicate` function needs a fallback path: when `input_hashes` is empty, search by scanning provenance records that match the `task_type` and `params_hash` directly. The metadata_json column in provenance can store the params_hash, or alternatively query the tasks table filtered by task_type and compare params hashes.

**Files:**
- `server/catgo/workflow/provenance.py` -- fix `find_duplicate()` to handle empty input_hashes
- `server/tests/test_provenance.py` -- verify tests pass, no changes expected

**Fix approach:**
```python
# In find_duplicate(), when input_hashes is empty, fall back to scanning
# all provenance records for the given task_type
if not input_hashes:
    # No input constraint -- search all tasks of this type
    conn = db._get_conn()
    rows = conn.execute(
```

### 1B: While Loop Tests (2 failing)

**Root cause:** `test_while_completes_on_condition` and `test_while_iterates_until_max` likely need more scan cycles. The while loop handler in `scanner.py` (line 82-167) transitions the loop task from WAITING->READY on one cycle, then processes children on subsequent cycles. With children that have their own WAITING->READY->RUNNING->COMPLETED transitions, plus the loop's own state re-evaluation, the 10/30 cycle counts may be insufficient in some timing scenarios.

However, looking more carefully at the code: the while loop handler runs inside `_execute_ready_local_tasks` which only processes tasks in READY state. After resetting children to WAITING (line 164), the loop itself goes to WAITING (line 165). On the next `advance_waiting_tasks` call, the loop goes to READY again -- but its children also need to be advanced. The issue is likely that `advance_waiting_tasks` treats tasks with `parent_task_id` differently, or children inside a while loop don't get advanced properly because their dependencies aren't being re-evaluated.

**Fix approach:** Add extra scan cycles (increase from 10 to 20 and 30 to 50), or investigate whether `advance_waiting_tasks` needs to handle children of while loops that have been reset. The children have `parent_task_id` set but may lack proper task_links, meaning `advance_waiting_tasks` might not move them to READY.

**Files:**

### 1C: Batch Submit Tests (5 failing)

**Root cause:** All 5 tests use `@pytest.mark.asyncio` decorator which requires the `pytest-asyncio` plugin. The working pattern used elsewhere in the codebase (see `test_broadcast.py` line 20-24) uses `asyncio.new_event_loop()` instead:

```python
def _run(coro):
    loop = asyncio.new_event_loop()
    try:
        return loop.run_until_complete(coro)
    finally:
        loop.close()
```

**Fix approach:** Remove `@pytest.mark.asyncio` from all 5 test functions, rename from `async def test_*` to `def test_*`, and wrap the async call with the `_run()` helper.

**Files:**
- `server/tests/test_batch_submit.py` -- convert 5 tests from pytest.mark.asyncio to new_event_loop pattern

**Example conversion:**
```python
# Before:
@pytest.mark.asyncio
async def test_batch_creates_array_script(db, workflow_id, config):
    ...
    job_id = await submit_batch_tasks(db, task_ids, workflow_id, config)
    ...

# After:
def test_batch_creates_array_script(db, workflow_id, config):
    def _inner():
        ...  # same body but wrapped
    loop = asyncio.new_event_loop()
    try:
        loop.run_until_complete(_inner_coro())
    finally:
        loop.close()
```

Or more cleanly, extract a module-level `_run` helper and use it:
```python
def _run(coro):
    loop = asyncio.new_event_loop()
    try:
        return loop.run_until_complete(coro)
    finally:
        loop.close()

def test_batch_creates_array_script(db, workflow_id, config):
    task_ids = _make_tasks(db, workflow_id, n=5)
    hpc = _mock_hpc()
    with patch(...):
        job_id = _run(submit_batch_tasks(db, task_ids, workflow_id, config))
    assert job_id == "99887766"
```

## Task 8: Provenance UI

**Current state:** `TaskDetailPanel.svelte` shows task info, params, parents/children links, and result. No provenance information.

**Approach:**

### 8A: Backend provenance API endpoint

Add `GET /api/v2/tasks/{task_id}/provenance` to the V2 router:

```python
@router.get("/tasks/{task_id}/provenance")
def get_task_provenance(task_id: str):
    """Return provenance lineage for a task."""
    from catgo.workflow.provenance import trace_provenance
    records = db.get_provenance(task_id)
    lineage = {}
    for rec in records:
        trace = trace_provenance(db, task_id, rec["output_key"])
        if trace:
            lineage[rec["output_key"]] = trace
    # Check for duplicates
    duplicate_info = None
    for rec in records:
        if rec.get("value_hash"):
            dupes = db.find_provenance_by_hash(rec["value_hash"])
            if len(dupes) > 1:
                duplicate_info = {
                    "hash": rec["value_hash"],
                    "matching_tasks": [d["task_id"] for d in dupes if d["task_id"] != task_id],
                }
                break
    return {"task_id": task_id, "lineage": lineage, "duplicate": duplicate_info}
```
